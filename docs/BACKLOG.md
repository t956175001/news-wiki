# BACKLOG — 想做但没做

> 开发过程中冒出的「顺手加一下会更好」的念头，一律记到这里，**不要实现**（`CLAUDE.md` 禁止清单第 5 条）。
> 这份清单还有一个用途：面试被问「还能怎么改进」时，直接照着答。

## 已知短板（按优先级）

### 1. 缺自动化评测集 ★ 最想补的
现状：Prompt 改动后靠人工抽检 20 条判断效果，不客观、不可复现。
设想：建 50 条金标准集（人工标注实体/概念/关系），每次 Prompt 变更跑一遍算 P/R/F1，结果按 `prompt_version` 分组存表，`/ops` 页加一个版本对比视图。
可行性：数据结构已经支持——每条 `Evidence` 都记了 `prompt_version`，按版本分组是现成的。

### 2. 实体消歧
现状：`normalized_name + entity_type` 唯一，同名不同实体会被错误合并（如两个不同的「小米」）。
设想：落库前用上下文做判别——比较候选实体的 summary 与已有实体的语义相似度，低于阈值则新建而非合并。

### 3. 谓词归一靠手工映射表
现状：`PREDICATE_ALIASES` 是硬编码的字典，覆盖不全。
设想：改为让模型从固定谓词词表里选（枚举约束），或用 embedding 对谓词聚类后取代表词。

### 4. 后台线程不够健壮
现状：进程重启会丢失执行中的任务，只能靠「启动时把超时的 running 标记为 failed」兜底。
设想：任务量涨到每分钟数十个时换 Celery。当前量级下不值得（ADR-004）。

### 5. 时间维度缺失
现状：实体信息是覆盖式更新，看不到「某个模型的参数量在三个月里被报道过几个不同数字」。
设想：给 Entity 加版本链或时间切片，词条页展示信息演变时间线。这个功能对资讯类知识库其实很有价值。

## 开发中产生的想法

> 实现阶段往下追加，格式：`- [日期] 想法 —— 为什么当时没做`

- [2026-08-28] 概念页（`/concept/:id`）—— 词条页优先，概念详情本期只在图谱里可见
- [2026-08-28] 图谱的时间轴回放（按日期看关系网络生长）—— 视觉效果好但工作量大，D10 排不下
- [2026-08-28] 正文长度下限（trafilatura 偶尔只抽出几十个字符就算成功，D2 实测有 61 字符的条目入库）—— ARCHITECTURE 没规定阈值，不想自己发明一个数字；这类条目喂给 D4 只是浪费 token，可考虑低于 N 字符标 `extract_status="skipped"`
- [2026-08-28] 两个中文源（机器之心/量子位）目前依赖自建 RSSHub —— 官方 feed 不存在（`jiqizhixin.com/rss` 返回 HTML 页面），公共 rsshub.app 实例 403，D2 先用占位 URL 灌进去，采集失败会记在 `RssSource.last_error` 上
- [2026-08-29] `scripts/check-clean.sh` 的禁用词是**子串**匹配，普通英文单词可能整词误报（D3 遇到一次，改了变量名绕开）—— 想过给词表条目加 `\b` 词边界，但放宽一个安全网需要先想清楚哪些词确实需要子串匹配，不适合顺手改
- [2026-08-29] GLM-4.7 的官网价没查到确切数字（官网对旗舰模型按 prompt 长度分档，单一「元/千 token」表达不了）—— `pricing.py` 暂用上一代 GLM-4.6 的 ¥5/百万 作为默认值，靠 `LLM_PRICE_*` 环境变量覆盖；跑真实抽取前应核对一次
- [2026-08-29] `validators.py` 里的 `_norm()` 与 D4 要写的 `normalize.py::normalize_name()` 是同一个公式，重复了一份 —— D4 落地 `normalize.py` 后应合并，D3 阶段不想为了复用先建一个只有一个函数的模块
- [2026-08-29] 智谱把「余额不足」也返回 HTTP 429（body 里 `code: 1113`），和真正的限流同码，所以会被白白重试 3 次 —— 要区分只能解析 provider 的 body，那是把 GLM 的错误码耦合进客户端；等真的浪费到钱了再说
- [2026-08-29] `uniq_linkage_triple` 在 DB 层其实拦不住重复：Postgres 的唯一约束把 NULL 视为互不相等，而 entity→entity 的边 `object_concept` 恒为 NULL —— 应用层的 `get_or_create` 挡住了（`IS NULL` 能匹配），但并发写入没有兜底。Django 5 的 `UniqueConstraint(nulls_distinct=False)` 能修，需要改 ARCHITECTURE 3.2 的字段契约 + 一次迁移
- [2026-08-29] `mention_count` 统计的是「被抽取到的次数」而不是「被提及的次数」：同一批文章重跑一次就 +1 —— 排序权重用它够了，但字段名有误导性
- [2026-08-29] Evidence 不去重，重跑同一批文章会为同一句话再建一条 —— 这是有意的（每条记着自己的 `run_id` 和 `prompt_version`，是溯源数据不是状态），但词条页需要按 `run` 或 `snippet` 折叠展示，否则同一句话会重复列出
- [2026-08-29] 价目表里没有 flash 系列（`glm-4-flash` / `glm-4.5-flash`），用它们跑时成本记 0 并打 warning —— 免费档记 0 其实是对的，但和「模型没登记」是同一条代码路径，分不出来
- [2026-08-29] 免费的 `glm-4.5-flash` 是推理模型，3 篇文章的语料（约 2.6k prompt token）在 120s 超时内跑不完，三次重试全部超时 —— 换 `glm-4-flash` 可跑通（87s/次）。如果以后要用推理模型，超时和 `EXTRACT_BATCH_SIZE` 都得往下调
- [2026-08-29] 重试是嵌套的：`GLMClient` 内部 tenacity 重试 3 次，`invoke_json` 外层又重试 3 次，最坏情况一个 step 打 9 次上游请求 —— D5 验收时把 `GLM_BASE_URL` 指向死端口实测，单次 run 卡了 17 分钟才落到 failed（120s 超时 × 9）。两层各有各的理由（内层管网络抖动，外层管 JSON 不合法），但连接类错误不该走外层重试；要分开得在客户端区分「网络失败」和「输出不可用」两类异常
- [2026-08-29] DRF 在进 view 之前就检查限流，所以一次参数校验失败的 400 也会消耗掉访客当天 3 次额度中的一次 —— 对演示场景无所谓，真要做得对，得在 `throttle_failure` 之外自己实现「成功才计数」
- [2026-08-29] `step_metrics` 里多了一个 ARCHITECTURE 3.3 没列的状态值 `"skipped"`（当天没有待抽取文章、或没有文章可写简报时）—— 比记成 `failed` 诚实，但 D11 的流水线面板要认这个值，届时应回头把它写进 3.3 的契约
