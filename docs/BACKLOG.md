# BACKLOG — 想做但没做

> 开发过程中冒出的「顺手加一下会更好」的念头，一律记到这里，**不要实现**（`CLAUDE.md` 禁止清单第 5 条）。
> 这份清单还有一个用途：面试被问「还能怎么改进」时，直接照着答。

## 已知短板（按优先级）

### 1. 缺自动化评测集 ★ 最想补的
现状：Prompt 改动后靠人工抽检 20 条判断效果，不客观、不可复现。
设想：建 50 条金标准集（人工标注实体/概念/关系），每次 Prompt 变更跑一遍算 P/R/F1，结果按 `prompt_version` 分组存表，`/ops` 页加一个版本对比视图。
可行性：数据结构已经支持——每条 `Evidence` 都记了 `prompt_version`，按版本分组是现成的。

### 2. 实体消歧
现状：`normalized_name + entity_type` 唯一，同名不同实体会被错误合并（如两个不同的「小米」）。
设想：落库前用上下文做判别——比较候选实体的 summary 与已有实体的语义相似度，低于阈值则新建而非合并。

### 3. 谓词归一靠手工映射表
现状：`PREDICATE_ALIASES` 是硬编码的字典，覆盖不全。
设想：改为让模型从固定谓词词表里选（枚举约束），或用 embedding 对谓词聚类后取代表词。

### 4. 后台线程不够健壮
现状：进程重启会丢失执行中的任务，只能靠「启动时把超时的 running 标记为 failed」兜底。
设想：任务量涨到每分钟数十个时换 Celery。当前量级下不值得（ADR-004）。

### 5. 时间维度缺失
现状：实体信息是覆盖式更新，看不到「某个模型的参数量在三个月里被报道过几个不同数字」。
设想：给 Entity 加版本链或时间切片，词条页展示信息演变时间线。这个功能对资讯类知识库其实很有价值。

- [2026-08-29] Evidence 不去重，重跑同一批文章会为同一句话再建一条 —— 这是有意的（每条记着自己的 `run_id` 和 `prompt_version`，是溯源数据不是状态），但词条页需要按 `run` 或 `snippet` 折叠展示，否则同一句话会重复列出

- [2026-08-29] 免费的 `glm-4.5-flash` 是推理模型，3 篇文章的语料（约 2.6k prompt token）在 120s 超时内跑不完，三次重试全部超时 —— 换 `glm-4-flash` 可跑通（87s/次）。如果以后要用推理模型，超时和 `EXTRACT_BATCH_SIZE` 都得往下调
- [2026-08-29] 重试是嵌套的：`GLMClient` 内部 tenacity 重试 3 次，`invoke_json` 外层又重试 3 次，最坏情况一个 step 打 9 次上游请求 —— D5 验收时把 `GLM_BASE_URL` 指向死端口实测，单次 run 卡了 17 分钟才落到 failed（120s 超时 × 9）。两层各有各的理由（内层管网络抖动，外层管 JSON 不合法），但连接类错误不该走外层重试；要分开得在客户端区分「网络失败」和「输出不可用」两类异常
- [2026-08-29] DRF 在进 view 之前就检查限流，所以一次参数校验失败的 400 也会消耗掉访客当天 3 次额度中的一次 —— 对演示场景无所谓，真要做得对，得在 `throttle_failure` 之外自己实现「成功才计数」
- [2026-08-29] `step_metrics` 里多了一个 ARCHITECTURE 3.3 没列的状态值 `"skipped"`（当天没有待抽取文章、或没有文章可写简报时）—— 比记成 `failed` 诚实，但 D11 的流水线面板要认这个值，届时应回头把它写进 3.3 的契约
- [2026-08-29] 词条详情里 `linkages[].object` 对入边取的是**主语**（关系的另一端），不是关系字面上的宾语 —— ARCHITECTURE 4.1 的例子只给了出边，没规定入边怎么填。按字面填「宾语」的话入边的 object 恒等于当前实体本身，前端渲染不出「X -[谓词]-> 本实体」。`direction` 已经说明了本实体扮演哪一端，所以 object 取另一端是唯一可用的解释；D9 做词条页时若发现别扭，应回头把这条写进 4.1
- [2026-08-29] 图谱节点的 `value` 用的是**关系度数**而不是 `mention_count` —— PRD 3.3 要求「节点大小按关系数量加权」，而概念根本没有 mention_count 字段。ARCHITECTURE 4.2 的例子里 `value: 17, symbolSize: 40` 本身就对不上 `min(60, 12+value*2)`，所以例子里的数字不能当契约用。Top-N 截断仍按 mention_count 排（实体）/度数排（概念）
- [2026-08-29] 实体搜索命中别名靠的是把 JSONField `Cast` 成 text 再 `icontains` —— JSONField 的 `contains` 是 JSON 包含语义（整元素相等），用户输入半个词永远匹配不上，而且各数据库支持度不一。代价是这个查询用不上索引，数据量上万后要换成 Postgres 的 GIN + `jsonb_path_ops` 或者干脆把别名拆成独立表
- [2026-08-29] `glm-5.3-flash` 实测：**语料大小不影响延迟**。3 篇 95.9s / 2 篇 111.3s / 1 篇 102.0s，思考链长度（16k-27k 字符）几乎与输入无关且主导耗时 —— 所以「调小 EXTRACT_BATCH_SIZE 提速」是错的，反而让同样的 6k 推理 token 摊到更少文章上，单位成本更高。官方文档明确 `thinking.type` 仅支持 `enabled`，关不掉
