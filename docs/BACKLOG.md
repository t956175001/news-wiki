# BACKLOG — 想做但没做

> 开发过程中冒出的「顺手加一下会更好」的念头，一律记到这里，**不要实现**（`CLAUDE.md` 禁止清单第 5 条）。
> 这份清单还有一个用途：面试被问「还能怎么改进」时，直接照着答。

## 已知短板（按优先级）

### 1. 缺自动化评测集 ★ 最想补的
现状：Prompt 改动后靠人工抽检 20 条判断效果，不客观、不可复现。
设想：建 50 条金标准集（人工标注实体/概念/关系），每次 Prompt 变更跑一遍算 P/R/F1，结果按 `prompt_version` 分组存表，`/ops` 页加一个版本对比视图。
可行性：数据结构已经支持——每条 `Evidence` 都记了 `prompt_version`，按版本分组是现成的。

### 2. 实体消歧
现状：`normalized_name + entity_type` 唯一，同名不同实体会被错误合并（如两个不同的「小米」）。
设想：落库前用上下文做判别——比较候选实体的 summary 与已有实体的语义相似度，低于阈值则新建而非合并。

### 3. 谓词归一靠手工映射表
现状：`PREDICATE_ALIASES` 是硬编码的字典，覆盖不全。
设想：改为让模型从固定谓词词表里选（枚举约束），或用 embedding 对谓词聚类后取代表词。

### 4. 后台线程不够健壮
现状：进程重启会丢失执行中的任务，只能靠「启动时把超时的 running 标记为 failed」兜底。
设想：任务量涨到每分钟数十个时换 Celery。当前量级下不值得（ADR-004）。

### 5. 时间维度缺失
现状：实体信息是覆盖式更新，看不到「某个模型的参数量在三个月里被报道过几个不同数字」。
设想：给 Entity 加版本链或时间切片，词条页展示信息演变时间线。这个功能对资讯类知识库其实很有价值。
