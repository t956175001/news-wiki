## 二、项目自述（面试开场 2 分钟）

**结构：问题 → 做法 → 难点 → 结果**

> 这个项目来自我实习时做的一个资讯处理工具。当时的做法是让大模型给文章打标签、写摘要——但很快发现一个问题：摘要写得再流畅，你也没法验证它对不对，读者只能选择信或不信。
>
> 所以我重做的时候换了个思路：**不直接生成文本，而是先做结构化抽取，再把每条结构化结论钉死在原文上**。具体是三步——先抽实体，再抽概念，最后抽关系。每一步的输出会作为下一步的候选集，比如抽关系的时候，主语和宾语必须逐字来自前两步抽出的清单，不在清单里的一律丢弃。这样能挡住模型自由发挥导致的实体裂变问题。
>
> 每条抽出来的结论都会存一条证据记录，包含原文片段、来源链接、置信度，还有抽取时用的 Prompt 版本号。前端点开任何一条关系，都能看到它是从哪句话、哪篇文章、用哪版 Prompt 抽出来的。
>
> 做的过程中最花时间的是让 LLM 的输出稳定可用。我写了一层 Schema 校验，区分两类错误：格式错误就重试，个别条目引用了不存在的 ID 就跳过并计数——不能因为一条脏数据让整批失败。另外还做了一个流水线面板，每次抽取的分步耗时、token、成本都记下来，这样调 Prompt 的时候能看到改动对成本和质量的实际影响。
>
> 现在线上跑着，每天早上八点 GitHub Actions 定时触发一次，抽取完自动生成一份带引用角标的简报。

## 三、高频追问与准备

### AI 工程类

**Q：LLM 返回的 JSON 不合法怎么办？**
A：分层处理。① `response_format={"type":"json_object"}` 先约束格式；② `json.loads` 失败或 Schema 校验失败，抛异常触发 tenacity 重试，最多 3 次指数退避；③ 重试耗尽则该步标记 failed，但**前面已成功的步骤结果保留**，整个 run 状态是 `partial` 而不是全部回滚；④ 异常消息里带响应前 1000 字的预览——这个细节在调试时救过我好几次，不然只能看到一句 "Expecting value: line 1 column 1"。

**Q：怎么防止同一个实体被抽成多个节点？**
A：三层。① 数据层：`normalized_name`（小写+空白归一）+ `entity_type` 联合唯一，`update_or_create` 落库；② Prompt 层：抽关系时把已抽出的实体清单喂进去，要求主语宾语逐字来自清单；③ 别名层：模型抽到的其他叫法存进 `aliases` 数组，合并时取并集。
补充：谓词也有同样问题——"发布/推出/上线"是一个意思。我维护了一张 `PREDICATE_ALIASES` 映射表做归一，映射不到的保留原样。

**Q：怎么保证证据片段真的来自原文，不是模型编的？**
A：落库前做子串检查——把证据和原文都去掉空白字符后比对。但这里有个取舍：**检查不通过我没有直接丢弃，而是保留并把置信度乘 0.8，同时在运行日志里计数**。因为模型经常有全角半角、引号样式的差异，严格丢弃会误杀大量正确证据。这个阈值是跑了实际数据后调的。

**Q：你怎么评估抽取质量？**
A：坦白说这一版没有做完整的自动化评测集，这是我知道的最大短板。目前是三个手段：① Schema 层的硬约束（引用了不存在的实体直接跳过并计数，这个数字能反映模型的表现）；② 证据子串检查的通过率；③ 人工抽检——每次调 Prompt 后随机抽 20 条看准确率。
如果继续做，我会建一个 50 条的金标准集，每次 Prompt 改动跑一遍算 P/R，这也是 Prompt 版本管理已经预留好的能力——因为每条证据都记了版本号，可以按版本分组对比。

**Q：为什么不用 function calling / structured output？**
A：GLM 的 `json_object` 模式已经能保证是合法 JSON，剩下的字段级约束我用自己的校验器做，好处是校验逻辑对我可见可测——我能给「raw_article_id 越界」「引用未知实体」这些情况写单测，也能自己决定哪些错该重试、哪些该跳过。用严格的 structured output 会把这层逻辑交给厂商，跨模型迁移时行为不可控。

**Q：成本怎么控制？**
A：三层。① 输入侧：正文截断 4000 字符，每批 5 篇；② 记录侧：每次调用记 token 并按价格表折算成人民币，存进 `ExtractionRun`；③ 熔断侧：日累计成本超阈值后，访客触发的入口全部转只读，只有带 cron token 的定时任务能继续跑。另外演示环境预置了数据，访客不操作也能看到全部功能，大部分人根本不会触发真实调用。

### 架构类

**Q：为什么不用 Celery？**
A：先看 Celery 解决什么问题——任务队列、重试、并发控制、分布式。我这个场景是每天几次任务，单机。为此引入 Redis + worker + beat 三个进程，在 2C2G 的机器上，运维成本和资源占用都超过收益。
我用的方案是：后台线程执行 + `ExtractionRun` 表存状态 + 前端轮询。状态存在数据库里，所以即使多 worker 也能正确查询。定时调度我放到了 GitHub Actions，好处是调度和应用解耦、容器重启不丢任务，而且运行记录是公开可见的。
代价我也清楚：进程重启会丢失正在跑的线程任务。我的兜底是启动时把超时仍处于 running 的记录标记为 failed。如果量级涨到每分钟几十个任务，我会换成 Celery。

**Q：为什么证据表用三个可空外键，不用 GenericForeignKey？**
A：因为要用数据库约束保证「有且仅有一个目标非空」。GenericForeignKey 做不到这个——它在数据库层就是两个普通字段，没法加 CheckConstraint，脏数据能直接写进去。而溯源是这个项目的核心卖点，脏数据一旦进库整个功能就不可信了。
另外 GenericForeignKey 不能 join，词条页要一次取出关系及其证据和文章信息，用 GFK 会变成 N+1 查询。代价是 ORM 层不够优雅，我认为这里完整性优先。

**Q：词条详情接口的 N+1 怎么解决的？**
A：`select_related` 处理外键（linkage → entity/concept，evidence → raw_article → source），`prefetch_related` 处理反向多对多和一对多。我在测试里用 `assertNumQueries` 把查询数卡在 10 条以内，这样以后有人改 serializer 引入了 N+1，测试会直接挂。

**Q：三步抽取要调三次 LLM，成本是不是翻倍了？**
A：是的，语料被重复喂了三遍，token 成本大约是单次调用的 2.5 倍。这是我明确接受的代价——换来的是关系抽取质量的显著提升和失败可定位。如果成本成为瓶颈，可以把第二三步合并，但会牺牲「概念不与实体重复」的约束效果。我做过对比，一次性抽全部时同一实体裂成多个节点的情况明显更多。

### 工程类

**Q：测试怎么写的？LLM 怎么测？**
A：所有 LLM 调用在测试里 mock，`conftest.py` 里有一个统一的 fixture 返回构造好的 `LLMResult`。重点测的是失败路径：返回非法 JSON、缺必填字段、引用不存在的文章 ID、引用未抽出的实体、重试耗尽。这些分支比正常路径更容易出 bug。
另外有一个集成测试，全 mock LLM 跑通从采集到简报的完整编排，断言各模型都有数据、run 状态正确。

**Q：为什么不用 Nginx？**
A：Caddy 自动申请和续期证书，配置几行搞定。Nginx + certbot + 续期 cron + reload 钩子，调试至少半天。我这个项目工期两周，这半天花在核心功能上收益更高。而且证书续期是最容易被遗忘的运维债——三个月后证书过期、简历链接变红，那才是真的损失。Nginx 我会写，但这里不是它的最佳场景。

**Q：为什么部署在香港不是国内？**
A：国内地域的服务器对外提供 HTTP 服务需要 ICP 备案，备案周期两到三周，还要求域名在境内注册商。作为一个演示项目，境外地域免备案、当天就能上线。选香港而不是更远的地区，是因为对国内用户的网络延迟最低。
还有一个细节：域名 DNS 我用的是 Cloudflare 的 DNS only 模式，没开代理。开了代理流量会绕到 Cloudflare 边缘节点，反而比直连香港慢，会把线路优势抵消掉。

### 反思类

**Q：这个项目你觉得哪里做得不够？**
A：三点。① **没有自动化评测集**——现在靠人工抽检判断 Prompt 改动的效果，不够客观，这是我最想补的；② **谓词归一靠手工映射表**——覆盖不全，更好的做法是用 embedding 聚类或者让模型从固定词表里选；③ **后台线程方案不够健壮**——进程重启会丢任务，目前只能靠超时清理兜底。
另外范围上我主动砍掉了 RAG 问答，因为它和证据溯源在展示价值上重叠，两周内我选择把一件事做深。

**Q：和你实习时那版比，改进了什么？**
A：最实质的一点：**原来的抽取管线其实只跑了第一步**。抽概念和抽关系的函数都写好了，但从来没被主流程调用，日志里的模式硬编码成 "entities_only"，所以概念和关系数永远是 0——图谱根本没有边。这次重做把三步真正串起来了。
另一个是 LLM 客户端原来直接返回 content 字符串，把 usage 丢了，导致 token 和成本完全统计不到。这次改成返回结构化结果，才有了后面的成本熔断和观测面板。

**Q：如果给你更多时间，下一步做什么？**
A：优先级排序：① 建评测集，把 Prompt 迭代变成有数据支撑的过程；② 实体消歧——现在同名不同实体（比如两个叫"小米"的）会被合并，需要引入上下文判断；③ 时间维度——同一个实体的信息会随时间变化，现在是覆盖式更新，应该做成有时效性的版本链；④ 那时候再考虑 RAG，把结构化的图和向量检索结合起来做问答。
