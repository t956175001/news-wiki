## ADR-001：云端不跑 Playwright，降级为本地可选 adapter

**背景**
原项目用 Playwright 爬新闻列表页。作为演示项目要部署到公网，需要决定是否保留。

**决策**
线上采集只走 **RSS/Atom + `httpx` + `trafilatura`**。Playwright 实现保留在 `apps/ingest/fetchers/playwright.py`，通过 `ArticleFetcher` Protocol 与其他 fetcher 同构，仅本地按需启用，不装进生产镜像。

**理由**
1. Playwright 镜像体积 1.5GB+，启动慢，2C2G 的 VPS 上跑起来吃紧，还要和 Postgres、Caddy 抢内存
2. 目标站点改版或上反爬，线上演示就挂了——**简历链接打不开是最坏的结果**
3. RSS 是站点主动提供的结构化输出，稳定、合法、无反爬风险
4. 抽象成 Protocol 后，"我做过 Playwright 爬虫"这个事实仍然可验证（代码在、测试在），同时展示了接口抽象能力

**代价**
- 只能采集提供 RSS 的站点。缓解：`article.py` 支持传入任意 URL 抓正文，覆盖大部分场景
- 少了一个"技术含量高"的视觉展示点

**面试可讲**：这是典型的「能力展示」vs「系统可靠性」权衡。把不可靠的能力做成可插拔，两者都要到了。

## ADR-002：三步串行抽取，而非一次性抽全部

**背景**
可以让 LLM 一次输出实体+概念+关系，也可以拆成三次调用串行执行。

**决策**
拆成三步：`extract_entities` → `extract_concepts`（入参含步骤 1 结果）→ `extract_linkages`（入参含步骤 1、2 结果）。

**理由**
1. **关系抽取必须有实体清单做锚**。不给清单，LLM 会自由发挥出各种叫法（"OpenAI"/"Open AI"/"OpenAI 公司"），导致同一实体在图里裂成多个节点。给定清单并要求"逐字来自列表"，可以把这个问题挡在 LLM 那一层
2. 单步输出更短，JSON 结构更简单，格式错误率显著低于一次性输出大而全的嵌套结构
3. 失败可以定位到具体步骤。步骤 2 挂了不影响步骤 1 已抽出的实体（`status="partial"`）
4. 每步独立记录 token 和耗时，观测面板才有东西可看

**代价**
- 三次调用，token 消耗和总耗时高于一次调用（语料被重复喂了三遍）
- 串行，无法并行加速

**缓解**：正文截断到 4000 字符、每批 5 篇控制单次上下文；如果成本成为问题，可以把步骤 2、3 合并（但会牺牲理由 1 的效果）。

**面试可讲**：这是「用工程手段约束 LLM」的具体例子——不是靠祈祷模型听话，而是靠把上一步的结果作为下一步的封闭候选集。

## ADR-003：证据（Evidence）独立建表，且强制单目标约束

**背景**
"每条结论可溯源"是本项目的核心卖点，需要决定证据怎么存。

**决策**
`Evidence` 独立成表，通过三个可空外键分别指向 `Entity` / `Concept` / `Linkage`，用数据库 `CheckConstraint("evidence_single_target")` 强制**有且仅有一个**非空。同时冗余记录 `prompt_key`、`prompt_version`、`extraction_run`。

**理由**
1. 一条实体可能有多条证据（多篇文章都提到），一对多必须独立建表
2. 三选一用数据库约束而不是应用层校验——**应用层代码会绕过，数据库约束不会**。脏数据一旦进库，溯源功能就失去可信度
3. 冗余 `prompt_version` 而不是 join 查询：prompt 会迭代，必须记录**抽取当时**用的是哪版，事后 join 拿到的是最新版，那是错的
4. 关联 `extraction_run` 使得"这条证据来自哪次运行、那次运行花了多少钱"可以打通

**代价**
- 三个可空外键在 ORM 层不够优雅（比不上 GenericForeignKey）
- 但 GenericForeignKey 无法用数据库约束保证完整性，且查询性能差、不能 join。**这里选择完整性优先**

**面试可讲**：可以从「为什么不用 GenericForeignKey」切入，聊数据完整性与 ORM 便利性的取舍。

## ADR-004：不引入 Celery / Redis，用后台线程 + GitHub Actions cron

**背景**
抽取是长任务（单批 30-90 秒），需要异步执行。标准答案是 Celery + Redis。

**决策**
不引入。定时任务由 **GitHub Actions `schedule`** 通过 HTTP 打后端的 cron 端点触发；用户手动触发的抽取用**后台线程**执行，立即返回 `run_id`，前端轮询 `/api/v1/ops/runs/{run_id}/` 看进度。

**理由**
1. 本项目的并发量是**每天几次**。为此引入 Redis + Celery worker + beat 三个进程，运维复杂度和资源占用远超收益
2. 2C2G 的 VPS 上，省下 Redis 的内存更有价值
3. `ExtractionRun` 表本身就是任务状态存储，配合轮询已经满足需求，不需要额外的 broker
4. GitHub Actions 的运行记录是**公开可见的证据**——面试官能直接看到这个项目每天真的在跑，这是 Celery beat 给不了的
5. 调度与应用解耦：容器重启不丢调度任务

**代价**
- 后台线程随进程重启而丢失。缓解：任务失败会留下 `status="running"` 的僵尸记录，加一个启动时把超时 run 标记为 `failed` 的清理逻辑
- 无法做任务重试队列、优先级、并发控制
- gunicorn 多 worker 时，线程在哪个 worker 里执行不确定（但因为状态存在数据库里，不影响查询）

**面试可讲**：这是主动的「不做」。面试官问"为什么不用 Celery"时，能说清楚 Celery 解决什么问题、这些问题在本项目是否存在，比无脑上 Celery 更能体现判断力。

## ADR-005：本期不做 RAG / 向量检索

**背景**
"AI 项目"的常见标配是 RAG 问答。是否要加。

**决策**
不做。不引入任何 embedding 模型或向量数据库。

**理由**
1. 只有 14 天。**两个卖点做深，胜过三个卖点做浅。** 结构化抽取 + 证据溯源已经是完整的叙事
2. RAG 问答和"证据溯源"在展示价值上高度重叠——两者都在回答"这个结论从哪来"。重复投入边际收益低
3. 本项目的核心主张是「先结构化，再溯源」，这与「向量检索 + 生成」是**两条不同的技术路线**。混在一起会让项目定位模糊
4. 数据规模（百篇量级）下，结构化查询比向量检索更精确

**代价**
- 少了一个高频面试关键词

**缓解**：在 README 的「后续规划」和 `docs/BACKLOG.md` 里写明 RAG 的设计思路（怎么切块、怎么和现有 Evidence 表结合、怎么评估），面试被问到时能讲清楚"我知道怎么做，我判断这期不该做"。

## ADR-006：前端与后端同源部署，不用 CDN

**背景**
最初计划前端放 Cloudflare Pages、后端放 PaaS。后来改为自购腾讯云香港 VPS。

**决策**
Caddy 同时服务前端静态产物和反代 `/api` 到 gunicorn，**前后端同源**。Cloudflare Pages 方案保留在 `DEPLOYMENT.md` 作为备选。

**理由**
1. 访客在中国大陆。腾讯云香港的直连线路对国内的稳定性优于 Cloudflare 免费版（`*.pages.dev` 存在 DNS 污染问题）
2. **同源 = 零 CORS 配置**，省掉一整类联调 bug（预检请求、凭据、Header 白名单）
3. 少一个平台要管，部署链路更短

**代价**
- 没有 CDN 加速，全球访问不如 Cloudflare
- 静态资源占用 VPS 带宽（20M 对 demo 流量足够）

**验证要求**：D12 用 ITDOG 实测两种方案的国内访问速度，**用数据确认这条决策**，结论回写本文档。

**D12 验证结果（2026-08-30）**：实际服务器落在阿里云首尔（不是本 ADR 决策时设想的腾讯云香港），"直连线路优于 Cloudflare"的前提本身需要重新验证。Cloudflare Pages 对比未完成——原计划用子域名单独接入以避免动主域名 DNS，但 Cloudflare 现在的建站流程不接受"仅子域名"作为独立 zone，要做自定义域名对比就得整域名迁移 NS，对一个演示项目成本不成比例，予以跳过。因此只有直连一侧的数据：ITDOG 290 个全国监测点，**100% 成功（0 失败）**，全部节点平均响应 0.712s，全部解析结果均为真实服务器 IP（无 DNS 污染）。数据本身没有指向"需要引入 CDN"的信号，本决策（同源直连、不用 CDN）维持不变；完整方案对比与实测细节见 `DEPLOYMENT.md` §8。

## ADR-007：域名 DNS 用「DNS only」，不开 Cloudflare 代理

**背景**
域名托管在 Cloudflare，解析到腾讯云香港 VPS 时可以选择开橙云（代理）或灰云（DNS only）。

**决策**
用**灰云 DNS only**，直接解析到 VPS 公网 IP。

**理由**
开橙云后流量会绕行 Cloudflare 边缘节点，国内用户的链路变成「用户 → Cloudflare 边缘（可能在境外且拥塞）→ 香港 VPS」，比直连香港更慢，**把腾讯云香港线路优化的价值抵消掉了**。

**代价**
- 暴露源站 IP，失去 Cloudflare 的 DDoS 防护和 CDN 缓存
- 对一个演示项目，这个风险可接受

**注意**：灰云模式下 Cloudflare 不提供证书，HTTPS 由 Caddy 自动申请 Let's Encrypt 证书。这也意味着 **80 端口必须对公网开放**（ACME HTTP-01 挑战需要）。

## ADR-008：反代用 Caddy，不用 Nginx

**决策**
`deploy/Caddyfile` + Caddy 容器，取代 Nginx + certbot。

**理由**
1. Caddy 自动申请和续期 Let's Encrypt 证书，配置只要几行。Nginx + certbot + 续期 cron + reload 钩子至少要半天调试
2. 14 天的工期里，这半天更该花在 D4 或 D9 上
3. 证书续期是最容易被遗忘的运维债——三个月后证书过期、简历链接变红，得不偿失

**代价**
- Nginx 是更常见的简历关键词
- 缓解：README 里说明这个取舍本身，比会写 Nginx 配置更能体现判断力

## ADR-009：数据库用 PostgreSQL 容器，本地和生产一致

**背景**
早期为省 PaaS 免费额度曾考虑 SQLite。改为自购 VPS 后重新评估。

**决策**
本地和生产统一用 **PostgreSQL 16 容器**，数据存具名卷。

**理由**
1. 有了完整 VPS，没有理由再用 SQLite。SQLite 会带来 gunicorn 只能单 worker 的约束（多进程写会锁），那是纯粹的自我设限
2. 本地与生产环境一致，避免"本地能跑线上挂"（JSONField 行为、并发、事务语义在两者间有差异）
3. `JSONField`（`step_metrics` / `citations` / `aliases`）在 Postgres 上有原生 jsonb 支持，可索引可查询

**代价**
- 本地开发需要起 Docker，不能纯 Python 环境跑起来
- 缓解：`docker compose up -d db` 一行命令

## ADR-010：全新 `git init`，不继承原项目历史

**背景**
本项目是实习期内部项目的公开重制版。

**决策**
新建空仓库，**只手工挑选文件内容**复制（见 `docs/MIGRATION.md`），不 fork、不导入任何 git 历史。

**理由**
1. **合规**：原仓库包含不宜公开的配置信息与内部标识。这类内容一旦推到公开仓库，即使后续删除，git 历史和各种镜像站也会永久保留
2. 干净的提交历史本身也是作品的一部分——面试官会看 commit 记录
3. 复制的是**通用工程代码**（LLM 客户端封装、异常体系、分页器），不涉及业务逻辑和公司资产

**代价**
- 失去"从 0 到 1 的开发历程"的 git 记录
- 缓解：本项目自己的 14 天提交历史就是新的开发历程，而且更规范（Conventional Commits）

**执行要求**：每次 commit 前跑 `bash scripts/check-clean.sh`，必须全部 PASS。禁用词列表存在 `.forbidden-terms`（不提交），这样公开仓库里既没有禁用词本身，也不会广播「要清理什么」。

## ADR-011：LLM 客户端返回结构化结果而非裸字符串

**背景**
原项目的 `GLMClient.chat()` 返回 `response.choices[0].message.content`，是个 `str`。

**决策**
改为返回 `LLMResult` TypedDict，含 `content` + `prompt_tokens` + `completion_tokens` + `total_tokens` + `model`。

**理由**
原实现丢掉了 `response.usage`，导致：
1. 无法统计 token 消耗 → 观测面板没有数据
2. 无法计算成本 → 预算熔断无从实现
3. 原项目的抽取日志里 `usage` 三个字段全是 `None`，是个已知但未修的缺陷

这是本次重做中一个**明确的改进点**，值得在 README 里点名。

**代价**
- 调用方要写 `result["content"]` 而不是直接用返回值，略啰嗦
- 某些兼容 endpoint 可能不返回 usage → 缺失时填 0，不抛错

## ADR-012：演示模式下的成本控制采用「预置数据 + IP 限额」双层策略

**背景**
公开演示项目，访客触发 LLM 调用会产生真实费用。

**决策**
1. `seed_demo` 预灌 80-100 篇已抽取好的数据，访客**零操作即可浏览全部功能**
2. 写操作走 DRF `ScopedRateThrottle`，匿名 IP 每天 3 次
3. `LLM_DAILY_BUDGET_CNY` 日预算熔断，超限自动切只读
4. cron 端点用 `X-Cron-Token` 保护，访客无法触发

**理由**
纯只读演示看不出"活的"感觉；完全放开会被刷爆。三次额度足够让访客体验一次真实抽取，同时最坏情况下的日成本可控。

**代价**
- 多写约半天的代码（限流 + 熔断 + 友好文案）
- 但这本身是**产品思维和成本意识的展示点**，README 里要写

**为什么不用"访客自带 API Key"**：转化率极低，几乎没人会为了看一个 demo 去掏自己的 key。预置数据的体验好得多。

## ADR-013：所有 LLM 调用收敛到 `invoke_json`，预算护栏挂在这一个点上

**背景**
D4 的三步抽取把「渲染 prompt → 调模型 → 解析 JSON → 校验 → 重试」这一整套逻辑写在
`apps/wiki/services/extract_pipeline.py` 的私有函数 `_invoke_json` 里。D5 要加的每日简报
需要同一套逻辑，同时日预算熔断要覆盖**所有**会花钱的调用。

**决策**
把这段逻辑提到 `apps/common/llm/invoke.py`：`invoke_json()` + `StepMeta`。
抽取三步和简报都走它，`check_budget(trigger)` 在函数开头调用一次。
`SchemaError` 随之从 `apps/wiki/services/validators.py` 移到 `apps/common/exceptions.py`
（重试策略要认它，而 `apps/common` 不能反向依赖 `apps/wiki`），validators 里重新导出，
调用方 import 路径不变。

**理由**
熔断如果按调用方一个个加，就有 N 个地方可能漏。收敛成一个入口后，
「这个项目会不会偷偷花钱」这个问题只需要看一个函数。
额外的好处是简报免费获得了和抽取相同的重试语义与 token 计费。

**代价**
- `apps/common` 依赖了 `apps.ops.models`（预算要读 `ExtractionRun.cost_cny` 汇总），
  common 不再是零依赖的最底层。备选是把 budget 放进 ops，但 ROADMAP 指定了
  `apps/common/budget.py`，且「花钱的护栏」放在共享层比放在观测 app 里更好找。
- `SchemaError` 的定义位置和它的语义文档（在 validators 里）分开了两处。

**顺带定下的两件小事**
- `LLM_DAILY_BUDGET_CNY=0` 解释为「全部拦下」而不是「不限额」。两种误解里，
  想省钱却被计费的人受的伤害更大。cron 仍然豁免。
- 异步触发端点（`/ops/cron/daily`、`/wiki/extract/`）返回 **202 Accepted** 而非 200：
  请求只是把任务排上了，真正的结果要轮询 `/ops/runs/{run_id}/` 才拿得到。

## ADR-014：默认模型换成 GLM-5.3-Flash，并为推理模型改造 LLM 客户端

**背景**
项目最初把 `GLM_MODEL` 默认值定为 `glm-4.7`（ARCHITECTURE 第 7 节）。2026-08-30 账户充值后实测，
决定改用 `glm-5.3-flash`：官网价 0.8 元／2.8 元每百万 token，比 4.7 低一个数量级，
而这个项目要的是结构化抽取，不是长文创作。

**决策**
默认模型改为 `glm-5.3-flash`（`.env.example`、`config/settings/base.py`、ARCHITECTURE 第 7 节同步）。
它是推理模型且**思考关不掉**（官方文档：`thinking.type` 仅支持 `enabled`），
所以 LLM 客户端跟着改了三处：

1. **默认走流式**（`stream=True` + `stream_options.include_usage`）。
   非流式下长请求会在 ~145s 被上游掐断——是 `APIConnectionError` 而不是超时，
   把 timeout 提到 300s 也没用。关系抽取因此从来没成功过。改流式后一次 221.8s 的调用一次就过。
2. **单次请求超时改成 `LLM_TIMEOUT_SECONDS` 环境变量**，默认 300s（原来硬编码 120s）。
   合适的值跟着模型走，而模型本来就是环境变量。
3. **`ContentFilteredError` 从 `LLMError` 分出来**。GLM 用 HTTP 400 + code 1301 表示安全拒答，
   这是策略判断不是故障：同样的 prompt 每次都会被拒，重试无意义。
   简报被拒时记 `skipped` 而非 failed。

**理由**
换模型本身是成本决定；三处改造是「用推理模型」这个决定的必然代价，不是可选优化——
不改流式，关系抽取就跑不出任何一条边，图谱没有边等于没有图谱。

**代价**
- 单次调用 85-220s，比非推理模型慢得多。一批 3 篇文章跑完三步约 8 分钟。
- completion token 是成本大头（实测 3 篇文章 28,614 completion vs 8,389 prompt）。
- 内容审查会拦掉一部分生成结果，包括纯学术语料。抽取步骤被拒时整批文章标 failed，尚无单篇跳过机制（见 BACKLOG）。
- `stream=False` 分支保留但生产不再走它。

**实测否定的一条**
原本打算把 `EXTRACT_BATCH_SIZE` 从 5 降到 2 来提速。实测：3 篇 95.9s、2 篇 111.3s、1 篇 102.0s——
思考链长度几乎与输入无关且主导耗时，调小批次不提速，反而让同样的推理开销摊到更少文章上。保持 5。

## ADR-015：图谱按「关系密度」选点，而非按提及次数截断

**背景**
`/api/v1/wiki/graph/` 从 D6 起就按 `mention_count` 取 Top-N。2026-08-31 在线上实测：
默认 `limit=150` 时返回 **150 个节点、37 条边、94 个孤立节点（63%）**。
不是抽取的问题——452 条关系全都在库里——是**选点规则**的问题。

两层原因，第二层直到修完第一层才暴露出来：

1. **排序键错了**。演示数据 360 个实体里 349 个 `mention_count=1`（每天独立跑，跨日实体几乎不重叠），
   按它排序等于随机切片，度数最高的节点反而被切掉。
2. **只换排序键还不够**。改成按度数排序后仍有 52/150 个节点没有可见的边：
   枢纽的邻居大多是叶子节点，叶子在截断线以下，于是枢纽被画上画布时身上一条线都没有。

**决策**
三条规则，都在 `apps/wiki/services/graph.py`：

1. 截断排序键改为**关系度数**，`mention_count` 降为 tiebreaker。
2. 新增 `min_degree` 参数，**默认 1**——孤立节点默认不显示。传 `0` 恢复旧行为。
3. 需要截断时不再按节点排名切，而是 **按边选点**（`_select_connected`）：
   把边按两端度数之和排序，依次收录两个端点直到节点预算用尽。
   这样进入画布的每个节点都至少带着一条边。

另新增 **ego 图**：`?center=e410&depth=1`，只返回某个节点的邻域。响应结构不变。

**理由**
图谱页要回答的是「谁和谁有关系」。一个没有边的节点对这个问题的贡献是零，
它只是一个走错页面的列表项。而在有限的画布预算下，**边才是稀缺资源，不是节点**——
所以预算应该花在边上。

ego 图是另一半答案：全局图无论怎么选点都难读，而「以 OpenAI 为中心的关系网」是可读的，
且能从词条页直接跳过来，把两个页面接成一条动线。

**实测（同一份演示数据，改前 / 改后）**

| 视图 | 节点 | 边 | 孤立节点 |
|---|---|---|---|
| `limit=50` | 50 / 50 | 5 → **48** | 41 → **0** |
| `limit=150`（默认） | 150 / 150 | 37 → **163** | 94 → **0** |
| `limit=300` | 300 / 300 | 258 → **295** | 21 → **0** |

**代价**
- `min_degree=1` 默认值意味着「库里有 640 个实体，图上只有一部分」，这是刻意的取舍；
  `min_degree=0` 是诚实的逃生口，且保留旧的按排名切法。
- 按边选点在极端参数下会退化：`limit=1` 装不下任何一条边，
  筛选条件也可能留下一批「关系全指向被筛掉的节点」的节点。这两种情况回落到按排名切，
  宁可画出孤立节点，也不要给出一张空画布——空画布会被读成「没有数据」。
- ARCHITECTURE 4.2 的 JSON 结构没变（新增的都是可选 query 参数），但**行为变了**，
  所以 4.2 的文字说明与 D6 的相关测试一并更新。

## ADR-016：采集范围收敛到国内 AI 资讯平台，并在入库前做主题过滤

**背景**
D2 定的种子源是 arXiv cs.AI + Hacker News + 两个指向公共 RSSHub 的中文源占位。
公共 RSSHub 实例返回 403/503，所以实际跑起来的只有 arXiv 和 HN——
**每日简报变成了英文论文摘要合集**。这个项目的读者是国内的面试官，供给和需求对不上。

**决策**
1. 启用六个国内源（2026-08-31 全部 `curl` 实测通过）：
   量子位、雷峰网、InfoQ 中文、极客公园、IT 之家、钛媒体。
2. arXiv、HN、机器之心 **置为 `enabled=False` 而非删除**——
   删行会级联删掉它们名下的全部 `RawArticle`，把已有的演示语料一起带走。
3. 新增 `apps/ingest/services/relevance.py`：中英混合关键词表，
   在 `fetch_source` 里**先于抓正文**判断，不相关则跳过并计入新的 `filtered` 计数。
4. 纯 AI 站（量子位、机器之心）走 `ALWAYS_RELEVANT_HOSTS` 白名单，不做关键词判断。

**理由**
- **量子位有可用 feed**。D2 的注释写「量子位没有 feed」，那是从 RSSHub 路由失败推断的，
  没有试过站点自己的 `/feed`。这次试了，200，10 条。
- 大多数可用的中文源是**泛科技媒体**，不是 AI 垂直媒体。只用纯 AI 源信噪比最高，
  但日均只有 10 篇，某天源站不更新就没有简报。加过滤是拿一点点误判换稳定的供给。
- **过滤放在抓正文之前**才有意义：泛科技源大部分条目会被拒，
  放在后面等于每条被拒的条目白花一次页面请求。
- 用关键词而不是再调一次 LLM：要判断的是「这篇是不是被归类为 AI 报道」，标题基本直接回答了这个问题；
  为管线里最便宜的一个决策再加一次模型调用，换来的是更难解释的失败模式。

**实测（2026-08-31 真实跑一遍六个源）**

```
sources=6 fetched=157 filtered=49 deduped=0 saved=107 failed=1 (371.6s)
  量子位      fetched=10  filtered=0   saved=10
  雷峰网      fetched=20  filtered=2   saved=18
  InfoQ 中文  fetched=20  filtered=7   saved=12
  极客公园    fetched=30  filtered=1   saved=29
  IT 之家     fetched=60  filtered=27  saved=33
  钛媒体      fetched=17  filtered=12  saved=5
```

正文抽取平均 3878 字，trafilatura 在这几个站上工作正常。

**关键词表是被实测改出来的，不是想出来的**
第一版有 `芯片`、`显卡`、`月之暗面`。用这 107 篇真实文章回测，抓进来的噪声包括：
存储芯片厂商 IPO、HBM3E 内存量产、**一副叫「月之暗面」的耳机**、手机系统渲染管线。
改法：`芯片` 收窄为 `AI 芯片`/`算力芯片`（AI 侧由 `算力`/`英伟达`/`gpu` 兜底），
删掉 `月之暗面`（它同时是一个普通中文词，Moonshot 的报道里 `kimi` 更常见），
`rag` 加空格填充（否则命中 `fragment`/`fragrance`）。
改完再回测：**多拒了 6 篇，全是上述噪声，没有误伤任何一篇真 AI 报道。**

**代价**
- 关键词表要人工维护，新词（新公司、新模型家族）出现时会漏。
- 泛科技源仍会漏进一些边缘条目（一篇提到 AI 的 PlayStation 访谈）。可接受：误判成本是几个 token。
- 机器之心仍然没有可用 feed，要自建 RSSHub 才能启用。
- 现有演示数据仍是英文 arXiv 语料，中文内容靠每日 cron 累积。

## ADR-017：前端首屏不依赖任何第三方源

**背景**
站点部署在首尔，域名是新注册的 `.cn`，主要读者在国内、且不少人在外企内网里打开它。
2026-08-31 排查可访问性时发现两处境外依赖：

1. `index.html` 用**渲染阻塞的 `<link>`** 从 `fonts.googleapis.com` 拉三种字体。
   该域名在中国大陆不可达——**国内访客会白屏到这个请求超时**。
2. `/api/v1/docs/` 从 `cdn.jsdelivr.net/npm/swagger-ui-dist@latest/` 加载 Swagger UI。

**决策**
两个都自托管：字体走 `@fontsource*` npm 包（只引 Latin 子集）打进产物，
Swagger UI 走 `drf-spectacular-sidecar`。
在此基础上，`deploy/Caddyfile` 加上 `default-src 'self'` 的 CSP。

**理由**
- 第 1 条是**确定的 bug**，不是理论风险。它一直没被发现是因为验证方式都绕开了它：
  ITDOG 只测首个 HTML 请求，本机 Lighthouse 走代理。
- 第 2 条除了同样的可达性问题，还是**供应链风险**：`@latest` 无版本锁、无 SRI，
  等于让第三方在我们自己的 origin 下执行任意脚本。这个项目的公开面就是一个演示站，
  能被篡改的入口越少越好。
- 顺带的好处：首屏零第三方 origin，企业代理少一个可拦截的点，CSP 也才写得下去——
  只要还挂着 Google Fonts，`default-src 'self'` 就不成立。

**代价**
- 产物多了约 190KB 的 woff2（其中只有 Latin 子集会被真正请求，各约 15-37KB）。
- 字体版本跟着 npm 依赖走，不再自动拿到上游更新。这对一个不会天天改的站点是好事。
- CSP 的 `style-src` 必须留 `'unsafe-inline'`（ant-design-vue v4 用 cssinjs 运行时注入样式），
  `/api/v1/docs/` 还要单独放宽 `script-src`（drf-spectacular 模板带内联脚本）。
  两处都记在 Caddyfile 的注释里，不是随手放宽的。

## ADR-018：图谱默认节点上限从 150 降到 100

**背景**
ADR-015 修好了选点规则之后，`limit=150` 确实能出 163 条边、0 个孤立点，
数字上没问题。但把两种上限在 1600×900 的画布上并排截图比一次，看到的是另一回事：

- `limit=150`：节点互相压着，标签重叠到读不出是哪个词，底部和右侧还溢出画布。
- `limit=100`：各簇分开，枢纽和它的叶子一眼能认出来，标签基本不打架。

力导向布局没有自动缩放（ECharts 的 `roam` 是补救手段，不是替代品），
`GraphChart.forceLayout()` 已经在按节点数反向压缩间距和加大 gravity，
但画布尺寸是固定的，节点数到某个点之后再怎么调参也只是把重叠挪个位置。

**决策**
`DEFAULT_LIMIT` 从 150 改为 100（`apps/wiki/services/graph.py`），
前端 `GraphView.vue` 的 `DEFAULT_NODE_LIMIT` 同步为 100。硬上限 500 不变，
页面滑块范围 20-300 不变。

**理由**
「一屏能读懂」比「一屏信息多」重要。图谱页要回答的是「谁和谁有关系」，
而重叠到看不清标签的节点对这个问题的贡献同样是零——和 ADR-015 里
「没有边的节点贡献为零」是同一条判断，只是这次的瓶颈从数据变成了像素。

两个默认值取同一个数，是因为前端在 `limit` 等于默认值时会把它从 URL 里省掉，
好让分享出去的 `/graph` 链接是干净的；两边不一致会让这条裸链接的含义在
前后端之间漂移。

**代价**
- 同一份演示数据下可见的边从 **163 条降到 95 条**，少了约 42%。
  这是实打实的信息损失，不是免费的——想看全的把滑块拉到 150 以上即可，
  `truncated` 标记和提示条会照常告诉访客发生了截断。
- 100 这个数是在 1600×900 的桌面画布上比出来的，没有为更小的视口单独调。
  窄屏下更合适的值多半更小，但目前没有移动端图谱的实测数据，
  按视口宽度动态定默认值属于过早优化，记进 BACKLOG。
